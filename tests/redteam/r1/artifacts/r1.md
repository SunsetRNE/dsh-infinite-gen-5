### 1. 提权面：SUID/SGID 权威集合与真实写判定

### 2. 命名空间、cgroup 与隔离强度

`/proc/self/ns/` 缺 pid 与 user 两条链，`/proc/1` 不存在，cgroup 落在 `apps/com.dsh.client`（memory 控制器）与 `apps/uid_10527/pid_27013`（unified）——三层指纹同向指向同一事实：**这不是 namespace 隔离，是 Android 应用沙箱 + proot 用户态重定向**。`/sys/fs/cgroup` 与 `/proc/sys` 均不可写，`/proc/sys/kernel/*` 可写项计数为 0，故容器内不存在改内核参数的路子。proot 证据链完整：环境变量 `PROOT_TMP_DIR=/data/user/0/com.dsh.client/files/linux/tmp`、`PROOT_LOADER_32=/data/app/~~HOFKSN81o_StZGUv0Xuonw==/com.dsh.client-9mw0jRGTM05knLQU3SlCnw==/lib/arm64/libprootloader32.so`，`/proc/self/maps` 中 3 处 proot 映射且路径前缀同源。

逃逸面清零：5 个容器运行时套接字 + 4 个内存/IO 设备全缺席（`/dev/block` 有 266 项但 `dm-79` 为 `brw------- root:root`，在 uid 10527 下不可开）；宿主路径 `/system`、`/apex` 可读属 bind 授权，`/data` 为 `drwx------ root:root`，`/data/data/com.dsh.client` 在 proot 映射下不可见，只有 `/data/user/0/com.dsh.client/...` 可达 —— 且那是本应用自己的私有目录。

判据：`ls /proc/self/ns/` 不含 `pid` 与 `user`（exit 2）；`cat /proc/self/cgroup` 含 `apps/com.dsh.client`；`for f in /proc/sys/kernel/*; do [ -w "$f" ] && echo W; done | wc -l` 为 `0`。

### 5. 方法论教训（负结果与证据固定）

1. `/proc/self/mountinfo` **不能**用 `cp` 落盘：`cp: skipping file '/proc/self/mountinfo', as it was replaced while being copied` —— cp 子进程里 `self` 重新指到自己。必须 `cat /proc/self/mountinfo > FILE`，由当前 shell 自身重定向。
2. 无留存的「安全」结论最危险：首轮限深 SUID 扫描返回 `SUID_SGID_TOTAL=0`，是**假阴性**；同一 `find` 在 `/usr/bin -maxdepth 1` 下能正确报出 mount/su/umount。任何负结果必须先做阳性对照（`stat -c %a /usr/bin/su` 须出 `4755`）才可采信。
3. `find / -xdev -type f -perm /6000` 在 proot 下不可用：120s 与 900s 两次均以 `rc=124`、`0` 行收场（proot 逐系统调用翻译，全盘遍历代价极高）。等价替代：目录限定 + `stat` 逐条判定。
4. 命名空间对比要先确认被比对象存在：拿 `/proc/1/ns/*` 与 `/proc/self/ns/*` 相减时空串相等会伪造出「SAME」结论；`/proc/1` 在本容器根本不存在（`No such file or directory`），该对比在本环境恒为伪。
5. `capsh --version` 不是 capsh 的旗标（走 usage 分支，exit≠0）；版本核验须用 `capsh --print` 或 `--help`。

判据：`grep -c 'rc=124' `/dev/null` 无意义，改以 `raw/suid_raw.txt` 与 `raw/suid_full.txt` 均为 0 字节、而 `raw/suid.txt` 为 6 行 225 字节为证 —— 超时与命中同框即教训 2、3 的原始证据。
