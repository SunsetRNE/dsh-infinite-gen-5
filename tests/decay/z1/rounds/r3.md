## 自有容器 inode 邻接对与 resolv.conf 写入者取证（R3）

授权范围：自有资产 / 授权只读观测；本容器内文件与 /proc/net 只读，网络部分只做 **本机自连**（127.0.0.1 / ::1），不发任何外部包。承接 R1（三源基线）、R2（归因缺口）链条，本轮只回答 R2 文末「仍未闭合」里本容器真能闭合的条目，闭合不了的直接写「架构上不可得」。

观测环境：Ubuntu 24.04.3 LTS（proot 承载，/proc/self/status 的真实 Uid=10527）、Linux 6.1.141-android14-11 aarch64、python3 3.12.3、kptr_restrict=2。

### 一、LISTEN inode 曲线：成对创建 vs 释放复用

**结论（闭合 R2 未知 ②，并覆盖 R2 一处表述）**：

1. **不存在释放复用**。8 轮 × 2 s 窗口内 `listen=14` 恒定，14 个「协议族+地址+端口」键的 inode **稳定=14、变化=0** —— 这一批监听 socket 是进程启动时一次性创建、长期持有，窗口内没有任何一条被重建（若为释放复用，会看到同一键的 inode 变大或出现空洞）。
2. **邻接对的机制是被证到具体连接上的，不是猜的**：R2 并列的三组邻接对里，`282953010 / 282953011` 是同一条 **loopback 连接的两端** —— 一条 v6 ESTAB 记录 local 60230 → peer 7890 持 inode 282953010，另一条 local 7890 → peer 60230 持 inode 282953011，即「客户端 socket + 服务端 accept socket」在一次 connect 中被背靠背创建，故 inode 连号。
3. `283189091 / 283189092` 本轮全表已不存在（该连接已关闭），旁证它们是短生命周期的 ESTAB socket；同窗口里 `283297840` 命中一条 v4 ESTAB（local 53296 → peer 443）。
4. **LISTEN 面只有一组邻接对**，即 3090 的两条 v6 行（258832308 / 258832309），8 轮内保持相邻且纹丝不动 —— 与 R2 一致的「两条独立 v6 条目」；R2 把三组邻接对并列而未区分所属平面，此处按平面拆分。
5. 全表最大 inode 在同一窗口由 283283506 涨到 283297840（**+14334 / 14 s**），而 LISTEN 侧最大值 282549463 不动 —— 分配水位单调上涨、监听项不动，两者方向相反，正是「监听持久 + 短连接高频生灭」的组合特征。

判据：重跑第一节脚本应打印 `键数=14 稳定=14 变化=0` 且每轮 `相邻对数=1 [(258832308, 258832309)]`；重跑第二节脚本应打印 `LISTEN相邻对=[(258832308, 258832309)]`、`ESTAB=94`、`全表最大inode=283297900`（后两个数字随快照浮动，仅结构与「lista 面仅 1 组邻接对」为恒定判据）。

**结论（把「谁在 2026-09-25 18:16 写入」定到类别）**：

1. **口径先钉死**：R2 记的「40 字节」是**目标文件内容长度**，本轮补上「符号链接自身长度 = 39」——`stat -c` 对该路径给的是**链接自身**的 ino/时间戳（2639604 / 18:16:25.144），跟随链接后内容 40 字节、sha256 与 R2 同值（196ffcd6…aa24），R2 的哈希与字节数**没有记错**，只是没区分「链接自身」与「链接目标」两个 inode。
2. **两个 inode 连号**：目标 2639603、链接 2639604，两者 st_dev 同为 65103（/etc 与 /run 也是 65103）。**目标先建、链接后建，相隔 16 ms**（.128132709 → .144132709）。

4. **写入面是一整批，不是单个服务**：18:16:00–18:17:00 这一分钟里 /etc 与 /run/systemd 下被写/新建 **59 项**，含 nsswitch.conf（18:16:15.252）、localtime/timezone（18:16:15.6–15.7）、services（ctime 18:16:17.808 而 mtime 保持包内 2021-03-27）、passwd-/shadow-（18:16:18.6）、pam.d（18:16:24.6），随后 18:16:25 出 resolv 这一对 —— 典型的**引导收尾批量写入**（系统目录 /run/systemd/{ask-password,machines,netif} 的 mtime 停在 18:14:04–18:14:05，是更早一步的 tmpfiles 阶段）。
5. **不是运行中的 systemd-resolved**：包已装（ii 255.4-1ubuntu8.17 arm64），但进程名样本里含 resolved 的进程 0 个，`/run/systemd/notify`、`/run/systemd/private` 不存在，`/run/systemd/resolve/` 下只有那一个 40 字节文件（resolved 真正跑起来会建 io.systemd.Resolve 套接字与 pid 文件）。
6. **不是 dpkg 直接投放**：`dpkg -S` 对两个路径都 rc=1（无归属）；提及 resolv 的 postinst 只有 2 个（systemd-resolved.postinst、systemd.postinst），其中 systemd-resolved.postinst 里 `run/systemd/resolve` 出现 5 次 → stub 走的是 resolved 的运行时路径，由构建期的安装/引导流程生成。
7. **不是本容器内的任何活进程**：fd 扫描 6 个进程、resolv 相关 fd 命中 0；`/var/log/bootstrap.log`（61237 字节，mtime 2026-09-25 17:19:54）里 resolv / nsswitch / systemd-resolved 命中行数 **0**，写它那一刻的动作没有落到这个日志里。

判定：写入者是**镜像构建期（2026-09-25 18:16:25）的引导流程进程**，与 /etc/passwd、nsswitch.conf、localtime 同一批；**具体是哪个二进制或脚本名 = 架构上不可得**（容器内没有构建日志、没有 audit、dpkg 不拥有该文件、无 fd 持有者可查、bootstrap.log 零命中）。要定到名字，需要镜像构建日志或镜像层 diff —— 那是本容器之外的材料。

判据：重跑第二节脚本，`stat` 应收 `ino=2639603`（目标）与 `ino=2639604`（链接）两个**连号**值且 st_dev 同为 65103；`wc -c < /etc/resolv.conf` 应为 40；`dpkg -S` 两条均 rc=1；fd 扫描应为 `命中 resolv 相关 fd=0`。其中「扫过进程数」随快照在 6~7 之间浮动（首跑 6、复核跑 7），**恒定判据是命中数 0**，不是被扫进程数；同理第一节的 `ESTAB=94`、`全表最大inode` 也是浮动的，仅结构与「LISTEN 面仅 1 组邻接对」可作恒定判据。

### 三、7890 语义：本机自连协议探测（闭合 R2 未知 ④）

命令（只连 127.0.0.1 / ::1，握手失败即停，不发任何外部包、不发 CONNECT）：

```bash
python3 - <<'PY'
import socket
def probe(addr,fam,tag,payload=None):
    try:
        s=socket.socket(fam); s.settimeout(2); s.connect(addr)
        if payload: s.sendall(payload)
        s.settimeout(1.5)
        try: r=s.recv(64); rs=r.hex(); rs=rs+" (空)" if not r else rs
        except socket.timeout: rs="timeout-无回包"
        print("%s | 连接=OK | 发送=%s | 回包=%s"%(tag, payload.hex() if payload else "无", rs))
        s.close()
    except Exception as e: print("%s | 连接失败=%s: %s"%(tag,type(e).__name__,e))
probe(("::1",7890),socket.AF_INET6,"7890 空连接(不发字节)")
probe(("::1",7890),socket.AF_INET6,"7890 SOCKS5 greeting",bytes([5,1,0]))
probe(("127.0.0.1",7890),socket.AF_INET,"7890 v4 空连接")
probe(("127.0.0.1",3090),socket.AF_INET,"3090 空连接(对照)")
PY
```

实测输出：

```text
7890 空连接(不发字节) | 连接=OK | 发送=无 | 回包=timeout-无回包
7890 SOCKS5 greeting  | 连接=OK | 发送=050100 | 回包=0500
7890 v4 空连接        | 连接=OK | 发送=无 | 回包=timeout-无回包
3090 空连接(对照)     | 连接=OK | 发送=无 | 回包=timeout-无回包
```

**结论（闭合 R2 未知 ④：7890 是代理，不是转发）**：

1. 发送 SOCKS5 版本协商（RFC 1928 的 VERSION/METHODS 字段，常量 05 01 00）后收到 **05 00** —— 服务端回「版本 5，选中 NO AUTHENTICATION」，即 **7890 是一台无认证的 SOCKS5 代理**。端口转发（REDIRECT/DNAT）不会对客户端握手做协议应答，只会原样转发或直接断开；无回包的空连接说明它收下连接后**等待协议头**，这正是一直等 CONNECT 请求的代理行为。
2. 协议层可达性与绑定面一致：`::`（全接口）监听、v4 与 v6 的 loopback 都能连上并拿到同一行为，而 v4 表里没有 7890 条目 —— 该监听是双栈 v6 socket 处理 v4 流量。
3. 与 inode 证据互相咬合：存在一条活跃的 loopback 会话（客户端 60230 → 7890 持 inode 282953010；7890 侧 accept 60230 持 inode 282953011），且 R2 已测 7890 的持有 uid 为 10428、该 uid 同时有 58 条 ESTAB、被 10428/10411/10385/10391 四个 uid 双向连接 —— 「本机客户端连入 → 代理侧对外发起」的代理形态成立。
4. 本轮**没有发出任何 CONNECT**，因此没有产生对外流量；「代理的对外出口走 tun0(172.19.0.1) 还是 rmnet_data5(10.202.11.230)」需要 Android 侧 socket→uid→进程归属，本容器结构性不可得（见未知 U2）。

判据：重跑第三节脚本，7890 的 SOCKS5 greeting 行**必须**回 `0500`（无认证方法被接受）；空连接行必须为 `timeout-无回包`（代理在等协议头，不会主动 say hello）。这两条同时成立即判定「代理」成立。

### 四、四态标签行

已知：LISTEN 面 14 键在 8 轮采样内 inode 零变化（稳定=14 / 变化=0）；邻接对 282953010/282953011 为一条 loopback 连接的两端（客户端 60230→7890、服务端 7890→60230）；7890 为 SOCKS5 无认证代理（05 01 00 → 05 00）；/etc/resolv.conf 与其目标 inode 连号（2639604 / 2639603）、同设备 65103、相隔 16 ms，写入面是 18:16 那一批 59 项引导收尾写入。
推测：/run/systemd/resolve/stub-resolv.conf 由构建期的 systemd-resolved 安装/引导流程按模板生成（依据：dpkg 不拥有该文件 + systemd-resolved.postinst 里 `run/systemd/resolve` 出现 5 次 + 同批 /run/systemd 目录 mtime 停在 18:14:04–18:14:05）。
