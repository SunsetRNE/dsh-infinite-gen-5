## 自有容器 网络归因缺口闭合观测（R2）

自有资产 / 授权只读观测：对象是本机容器与其宿主手机的 `/proc` 与 `/etc`，本轮只读，不改配置、不写目标、不做攻击动作。承接 R1 基线（/root/dsh-infinite-gen-5/tests/decay/z1/rounds/r1.md），本轮目标是把 R1 列出的未闭合未知 ①②⑤ 用**新的命令面**推到可判定。

观测时刻（本轮实测）：2026-09-29T06:50:54Z，`date -u` rc=0。环境复核：内核 6.1.141-android14-11-o-g659d588fa0da aarch64；glibc 2.39-0ubuntu8.9（`ldd --version`）；`/proc/self/status` 的 `Uid:` / `Gid:` 四元组均为 10527，而 `id -u` / `id -g` 返回 0；`getent passwd 10527` rc=2（/etc/passwd 仅 22 行，无该 uid 条目）。

### 一、闭合未知①：12 条无归因 LISTEN 的 PID / UID

新命令面：全扫 `/proc/[0-9]*/fd` 取 `socket:[inode]` 集合，与 `/proc/net/tcp`、`/proc/net/tcp6` 的 inode 列做双向对齐（R1 未做这一步，R1 只看了 `ss -ltnp` 的 users: 字段）。

原始结果片段：

tcp6 LISTEN=7 归因=0 无归因=7 | ESTAB=33 归因=0 无归因=33

采样抖动（同一轮内三次采样，逐次如实记录）：socket inode 24 / 23 / 23；fd 可读进程 5（持 socket 者）/ 8 / 7（后两个是"fd 目录可列"的进程数，口径不同不得混用）；LISTEN 侧三次恒为 7 + 7，一条不多一条不少；ESTAB 侧 tcp 69 / 71 / 69、tcp6 33 / 35 / 44，合计在 102 ~ 113 之间漂移。**因此本轮可作结论的是归因结构（谁在归因、归到谁），不是计数本身** —— 后文正文引用的是第二次采样。

### 三、闭合未知⑤：/etc/hosts 为 0 字节时 nsswitch 的解析路径

新命令面：`getent` 三路 + `socket.getaddrinfo` + 解析器直查（自造 DNS 查询包），不依赖已缺失的 nc / dig。

原始结果片段：

```

rc_localhost=2        （getent hosts localhost → 无输出）
rc_ah4_real=2 lines=0 （getent ahostsv4 localhost）

  8.8.8.8 rcode=0 ancount=2 rdlen=61
  223.5.5.5 rcode=0 ancount=2 rdlen=61
```

- 顺序判定：`/etc/nsswitch.conf`（526 字节）的 hosts 行逐字为 `hosts:          files dns`，**没有 myhostname / resolve / mdns 模块**。`files` 模块读 `/etc/hosts`（0 字节，mtime 2026-09-25 17:19）必然 miss，于是全部落到 `dns`。
- 模块可用性：`/lib/aarch64-linux-gnu/` 下 libnss_dns.so.2、libnss_files.so.2、libnss_compat.so.2、libnss_hesiod.so.2、libnss_systemd.so.2 均在，glibc 2.39-0ubuntu8.9 走 dlopen 加载 nss 模块的路径通畅。
- 可直接观测的后果：凡只有 hosts 文件能答的名字（localhost、android.localdomain）在本容器内均不可解析 —— `getent hosts localhost` rc=2 且零输出，`socket.getaddrinfo('localhost', 80)` 抛 `socket.gaierror: [Errno -2]`。需要 DNS 才能答的名字正常：`getent hosts example.com` rc=0，且返回的是 IPv6 优先记录。
- 解析器链路：`/etc/resolv.conf` → `../run/systemd/resolve/stub-resolv.conf`（readlink -f 得 /run/systemd/resolve/stub-resolv.conf，40 字节，sha256:196ffcd6cdc9fe42c33670496b4927b66366c4694d0213e2e0643a0962a7aa24，与 R1 同值、本轮未变）；内容为 `nameserver 8.8.8.8` 与 `nameserver 223.5.5.5`。该目录下只有这一个文件、没有 systemd-resolved 的运行痕迹，说明它是被静态写入的配置，而不是 resolved 自己生成的 stub（真正的 stub 会写回环地址的 53 端口）。
- 两台上游均应答：直发查询包到 8.8.8.8:53 与 223.5.5.5:53，都返回 rcode=0、ancount=2、响应 61 字节 —— 出网 DNS 通，但完全绕开了本机 hosts 表。

### 四、顺带闭合 R1 的一处"对不上"，并覆盖 R1 的一处表述

- R1 记「id 返回 uid=0 与环境记载 uid=10527 冲突」：实测两层视图并存 —— `id -u` 走 libc 包装返回 0，`/proc/self/status` 的内核记录是 `Uid: 10527 10527 10527 10527`。取内核值，冲突消解。
- R1 记「3090 为双栈同 socket 两形态」：本轮证否 —— 两条 LISTEN 的 inode 不同（258832309 与 258832308），且 tcp 表中根本不存在 3090 条目；同一 inode 同时出现在 tcp 与 tcp6 表的只有占位 inode 0。按实测应写成"两条相邻 inode 的独立 v6 监听条目"。

### 五、主件：inode 双向对齐脚本（本轮真正跑过的实现）

```bash
cat > /tmp/r2_inode_join.py <<'PY'
import os, re, socket, struct
def parse_net(p):
    out = {}
    for ln in open(p).read().splitlines()[1:]:
        f = ln.split()
        if len(f) < 10: continue
        out[f[9]] = {"local": f[1], "rem": f[2], "st": f[3], "uid": f[7], "ino": f[9]}
    return out
def ip4(h): return socket.inet_ntoa(struct.pack("<I", int(h, 16)))
def ip6(h): return socket.inet_ntop(socket.AF_INET6,
    b"".join(bytes.fromhex(h[i:i+8])[::-1] for i in range(0, 32, 8)))
def split(a, v6=False):
    h, p = a.rsplit(":", 1); return (ip6(h) if v6 else ip4(h)), int(p, 16)
tcp, tcp6 = parse_net("/proc/net/tcp"), parse_net("/proc/net/tcp6")
fd_inodes, seen = set(), 0
for pid in os.listdir("/proc"):
    if not pid.isdigit(): continue
    try:
        fds = os.listdir("/proc/%s/fd" % pid); seen += 1
    except Exception:
        continue
    for fd in fds:
        try: t = os.readlink("/proc/%s/fd/%s" % (pid, fd))
        except Exception: continue
        m = re.match(r"socket:\[(\d+)\]", t)
        if m: fd_inodes.add(m.group(1))
print("fd可见socket inode总数:", len(fd_inodes), "有fd可读进程数:", seen)
for tag, net, v6 in (("tcp", tcp, False), ("tcp6", tcp6, True)):
    lis = [v for v in net.values() if v["st"] == "0A"]
    est = [v for v in net.values() if v["st"] == "01"]
    ul = [v for v in lis if v["ino"] not in fd_inodes]
    ue = [v for v in est if v["ino"] not in fd_inodes]
    nlb = sum(1 for v in est if not split(v["rem"], v6)[0].startswith("127."))
    print("%s LISTEN=%d 归因=%d 无归因=%d | ESTAB=%d 无归因=%d 非环回=%d"
          % (tag, len(lis), len(lis)-len(ul), len(ul), len(est), len(ue), nlb))
    for v in ul:
        lip, lp = split(v["local"], v6)
        print("  无主LISTEN %s:%d uid=%s ino=%s" % (lip, lp, v["uid"], v["ino"]))
PY
python3 /tmp/r2_inode_join.py
```

### 七、本轮仍未闭合的未知（供 R3）

1. **12 条无主监听的进程名 / 包名**：uid 已定位到 10088 / 10378 / 10385 / 10428 / 10527，但 Android 侧 PID 不在本 PID ns，`/proc/*/fd` 全扫得 0 命中；需改走 App 层接口或设备 shell 按 uid 反查包名。
2. **三组 inode 邻接对的性质**：258832308 / 258832309、282953010 / 282953011、283189091 / 283189092 差值为 1；是"同一进程成对创建的 socket"还是"释放后复用"，需连续采样 inode 差值曲线，本 ns 内看不到持有者。
3. **172.19.0.1:40379 的对端 172.19.0.2 是谁**：本轮只拿到 uid=10428 与 tun0 网关身份，隧道对端与业务归属未定。
4. **7890 的语义**：本轮确认它是 uid=10428 持有的 LISTEN 且被四个 uid 双向连接（既作 local 又作 rem），代理 / 转发二选一仍无法判定 —— 需要读到该端口持有者的配置。
5. **uid → 包名映射表**：需要 `/data/system/packages.list` 或 `pm list packages -U` 这类宿主侧数据，本容器权限下不可读。
6. **/etc/resolv.conf 的写入者**：文件名叫 stub-resolv.conf，内容却是两台公网解析器、且目录内只有这一个文件、无 resolved 运行痕迹；是谁在 2026-09-25 18:16 写入了它，本容器内无证据。
