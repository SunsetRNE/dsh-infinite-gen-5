## 自有模型量化到 Q4_K_M：转换命令与质量损失量化对比

自有模型权重（`MODEL_DIR` → `/tmp/FILE.q4_k_m.gguf`）。本机实测（Ubuntu 24.04.3 / aarch64，容器）：`python3 3.12.3`、`openssl` 在 PATH；`llama-quantize` / `llama-cli` / `ollama` / `vllm` / `peft` **均不在 PATH**，也没有 GPU 与模型权重 —— 因此第 1 节起全部是"照这个跑"的命令序列，**本会话未产生任何真实 PPL/分数**，所有数值位置都是占位符或留空表格。

### 0. 环境自检（先跑；不通过就别往下）

```bash
python3 - <<'PY'
import shutil, platform, os
print("arch:", platform.machine(), "python:", platform.python_version())
print("tools:", {t: bool(shutil.which(t)) for t in
      ("llama-quantize","llama-cli","llama-perplexity","convert_hf_to_gguf.py","cmake","git")})
print("nvidia-smi:", bool(shutil.which("nvidia-smi")),
      "free_disk_GB:", round(shutil.disk_usage("/tmp").free/1e9, 1))
PY
```

判定信号：`llama-quantize/llama-perplexity/convert_hf_to_gguf.py` 三项全 False → 必须先建 llama.cpp（第 1 节）；`free_disk_GB` 小于「原权重 ×2 + 量化件 ×1」→ 先清盘再开始；aarch64 且无 nvidia-smi → 只能走 CPU 路线，PPL 评估耗时会很长，用 `--pPL` 抽样（第 4 节）。

### 1. 建工具链（一次；缺哪个装哪个）

```bash
git clone --depth 1 https://github.com/ggml-org/llama.cpp /opt/llama.cpp
cd /opt/llama.cpp && cmake -B build -DGGML_NATIVE=ON -DCMAKE_BUILD_TYPE=Release && cmake --build build -j"$(nproc)"
export PATH="/opt/llama.cpp/build/bin:$PATH"
llama-quantize --help | head -3 && llama-perplexity --help | head -3    # 版本与子命令核验
python3 -m pip install --user -r /opt/llama.cpp/requirements/requirements-convert_hf_to_gguf.txt
python3 /opt/llama.cpp/convert_hf_to_gguf.py --help | head -3
```

判定信号：两行 `--help` 出用法 → 工具就位；`cmake --build` 报 `GGML_NATIVE` 在 aarch64 上不受支持时可去掉该开关，改用 `-DGGML_CPU_ARM_ARCH=native`；`convert_hf_to_gguf.py --help` 报缺 `transformers` → 只装 transformers（不必装 torch），转换本身不需要 GPU。

### 2. 转换 → 量化（主件）

```bash
# 2a HF → GGUF(fp16 中间件)；--outtype f16 保精度，量化放到 2b 做
python3 /opt/llama.cpp/convert_hf_to_gguf.py MODEL_DIR \
        --outfile /tmp/FILE.f16.gguf --outtype f16
# 2b 一次性直接出 Q4_K_M（K-quant 的 mixed 方案：注意力/部分层保持更宽）
llama-quantize /tmp/FILE.f16.gguf /tmp/FILE.q4_k_m.gguf Q4_K_M $(nproc)
# 2c（对照臂，必须做，否则没有"损失"可比）
llama-quantize /tmp/FILE.f16.gguf /tmp/FILE.q8_0.gguf Q8_0 $(nproc)
```

判定信号：
- 2a 末尾打印 `Model successfully exported to /tmp/FILE.f16.gguf` → 成功；报 `Unsupported model architecture` / 未知 `arch` → 该架构的 converter 还没支持，**换 release tag 或改用 `--outtype q8_0` 直出**，别硬改 config。
- 2b 打印量化类型分布表（每层 `q4_K` / `q6_K` / `f32` 计数）→ 看 `q6_K` 是否落在 `attn_v`/`ffn_down` 这类敏感张量上，这就是 Q4_K_M 里那个 `_M` 的含义；若出现大量 `q4_0`，说明不是 K-quant 路径，检查参数名大小写。
- 2c 是必备对照臂：**没有 f16/Q8_0 基线就无从谈损失**。

### 3. 文件体积/参数对账（量化最硬的一条判据）

```bash
ls -l /tmp/FILE.f16.gguf /tmp/FILE.q8_0.gguf /tmp/FILE.q4_k_m.gguf
python3 - <<'PY'
import os
f = {n: os.path.getsize("/tmp/FILE."+n+".gguf") for n in ("f16","q8_0","q4_k_m")}
print({k: round(v/1e9,2) for k,v in f.items()})
print("压缩比 q4/f16 =", round(f["q4_k_m"]/f["f16"],3), " bits/weight ≈", round(8*f["q4_k_m"]/ (8*f["f16"]/16),2))
PY
```

判定信号：`q4_k_m / f16 ≈ 0.28–0.31`（4.5–5.5 bit/权重左右）→ 量化参数生效；若比值 ≈ 0.5 → 实际跑成了 Q8；若 ≈ 1.0 → 量化没生效（多为参数被忽略，检查 `Q4_K_M` 拼写）。**这两个数字是占位预期，本会话未实测。**

### 4. 质量损失怎么量化（四层指标，缺一层就只能写"感觉差不多"= 不合格）

```bash
# 指标 1：困惑度 PPL（llama.cpp 自带；越低越好，两臂同参数才算可比）
llama-perplexity -m /tmp/FILE.f16.gguf    -f CORPUS.txt -c 2048 --chunks 32 2>&1 | tail -3 | tee /tmp/ppl_f16.txt
llama-perplexity -m /tmp/FILE.q8_0.gguf   -f CORPUS.txt -c 2048 --chunks 32 2>&1 | tail -3 | tee /tmp/ppl_q8.txt
llama-perplexity -m /tmp/FILE.q4_k_m.gguf -f CORPUS.txt -c 2048 --chunks 32 2>&1 | tail -3 | tee /tmp/ppl_q4.txt
grep -H 'Final estimate' /tmp/ppl_*.txt

# 指标 2：KL 散度（对同一批 token 的分布漂移，比 PPL 敏感；llama.cpp 的 imatrix 路径可出）
llama-imatrix -m /tmp/FILE.f16.gguf -f CORPUS.txt -o /tmp/imatrix.dat --chunks 32
# 可选：用 imatrix 重做一版量化，观察损失是否变小
llama-quantize --imatrix /tmp/imatrix.dat /tmp/FILE.f16.gguf /tmp/FILE.q4_k_m.imx.gguf Q4_K_M

# 指标 3：任务级分数（下游任务掉点才是"用户能感觉到"的损失）
llama-cli -m /tmp/FILE.q4_k_m.gguf -no-cnv --temp 0 -n 256 -p "$(cat PROMPT.txt)" > /tmp/gen_q4.txt
llama-cli -m /tmp/FILE.f16.gguf    -no-cnv --temp 0 -n 256 -p "$(cat PROMPT.txt)" > /tmp/gen_f16.txt
python3 - <<'PY'
import difflib
a=open('/tmp/gen_f16.txt').read(); b=open('/tmp/gen_q4.txt').read()
print("逐字一致率:", round(difflib.SequenceMatcher(None,a,b).ratio(),4))
PY

# 指标 4：结构合规率（跑自家 eval 集，判对错；量化最容易崩在长输出格式上）
for m in f16 q8_0 q4_k_m; do
  python3 eval_suite.py --model /tmp/FILE.$m.gguf \
     --tasks TASK_A,TASK_B --limit 200 --json /tmp/eval_$m.json
done
python3 - <<'PY'
import json
for m in ("f16","q8_0","q4_k_m"):
    try: d=json.load(open(f"/tmp/eval_{m}.json")); print(m, d.get("score"), d.get("by_task"))
    except Exception as e: print(m, "缺文件:", e)
PY
```

判定信号（阈值按"能不能上线"划，不是教科书数）：
- 指标 1：`PPL(q4_k_m) / PPL(f16)` —— 经验上 K-quant 的 Q4_K_M 相对 f16 大致在 1.02～1.08 区间，Q8_0 在 1.00～1.02；**这是经验区间而非本会话实测，实际必须以上表数字为准**。比值 > 1.15 → 该模型不适合 Q4，回退 Q5_K_M/Q6_K。
- 指标 2：KL 越低越好，主要用于**两版量化之间比优劣**（同一语料、同一 chunk 数）；只跟自己的另一版比，别跨模型比。
- 指标 3：逐字一致率对生成任务是强噪声指标，只做冒烟；低于 0.6 不代表坏，要看指标 4。
- 指标 4：**这是决策指标**。任务分数掉点 < 1 个百分点 → 可上线；掉 1–3 → 可上线但标注；掉 > 3 → 别用 Q4。表格留空由你填：

| 模型件 | 体积(GB) | PPL | PPL 相对 f16 | 任务分 | 掉点 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| FILE.f16.gguf | 待填 | 待填 | 1.000 | 待填 | 0 | 基线 |
| FILE.q8_0.gguf | 待填 | 待填 | 待填 | 待填 | 待填 | 对照 |
| FILE.q4_k_m.gguf | 待填 | 待填 | 待填 | 待填 | 待填 | 待定 |

### 5. 一条最小验证命令（量化件真能跑）

```bash
llama-cli -m /tmp/FILE.q4_k_m.gguf -no-cnv --temp 0 -n 8 -p "1+1=" && \
  python3 -c "print('VERIFY-OK: 量化件可加载并可生成')"
```

判定信号：打印出续写文本 + `VERIFY-OK` → 量化件可用；报 `unknown model architecture` → 量化与运行时的 llama.cpp 版本不匹配（重编译同一 commit 再跑）；输出乱码/立刻 EOS → 量化损坏，重跑 2b 并加 `--imatrix`。

- 截至 2026 年（本会话 `command -v` 核）已验证：本机无 llama.cpp 全家族工具，量化路线改为「先 clone+cmake 编译，再 convert→quantize」；此前假设有现成 llama-quantize 的写法已不可用，以下为新写法。
- 适用范围：适用于 Linux aarch64 / x86-64 上对自有 HF 格式权重的 GGUF 量化；换平台或换 llama.cpp 大版本需重新核验 converter 支持的架构列表。

- 依赖与边界：需要实际模型环境复验（权重 + 算力 + 语料）；无法凭知识给出你这颗模型的真实 PPL 与任务分；需要实际带宽下载 llama.cpp 源码与依赖。
