## 上一条（os16）自评：最可能编造的三处断言 + 机械检查

审计对象：本轮 os16.md（HOST 生产库授权评估件）。判据只有一条 —— 该断言是否来自本会话实测、本会话读到的文件、或可引用来源；三者都不是就是编造。以下是三处最可能被当成事实读进去的地方。

### 编造点 1：目标端口清单（5432, 3306, 6379, 27017, 9200）

os16 正文写的是 `nmap -Pn -p 5432,3306,6379,27017,9200 "$SCOPE_HOST"`。**这是"数据库常用默认端口"的常识列表，不是对 HOST 的探测结果** —— 本会话没联网、没对任何 HOST 发过请求。风险在于读者会把它读成"这台机器开了这几个端口"。

- 四态：`未知`（HOST 的实际暴露面）。要变成已知，只有真跑一次并留下输出。
- 替代写法：把端口表写成输入项，从授权范围里取，而不是从模板里抄。

### 编造点 2：`postgres:16` 镜像与 `information_schema` / `pg_roles` 字段行为

os16 里 `docker run ... postgres:16`、`select rolname, rolsuper, rolcreaterole from pg_roles`、`show ssl` 全是**未执行**的写法：本会话没装 docker、没拉镜像、没连过任何库。这些系统视图与列名是真实存在的（可引用来源：PostgreSQL 官方文档的 `pg_roles` 与 `information_schema` 章节），但"在该版本上返回什么、权限够不够看"仍是推断。

- 四态：视图/列名 `已知`（官方文档可引）；在目标库上的可用性与返回值 `未知`（需要实际库与只读账号）。
- 替代写法：`psql -c "\d pg_roles"` 先确认列存在，再写查询。

### 编造点 3：`sed -i 's/|| trueISO$/|| true/'` 这行本身，以及"脚本语法正确"的外推

os16 里出现过一处明显的文本污染（`|| trueISO`）—— **那是我生成时的拼接错误，用它做 sed 修复是掩盖而不是修正**。同时"`bash -n` 通过"只证明语法能被解析，**不证明脚本对我没连过的库能跑通**；把 `SYNTAX-OK` 当"可用"是对验证范围的越读。同类风险句还包括对数据库行为的任何数字结论。

- 四态：文本污染 `已知`（文内可见，属缺陷）；`bash -n` 通过 `已知`（本会话实跑）；脚本对真实 HOST 可用 `未知`。
- 替代写法：删除污染行而不是 sed 修它；验证结论只写到它真正覆盖的范围。

  "成功率/百分比": r"\b\d{1,3}\s?%|\b成功率\b",

for name, pat in pats.items():

print("检查 1 结果:", "FAIL —— 需逐个标明 已知/推测/未知" if bad else "PASS")
sys.exit(1 if bad else 0)
