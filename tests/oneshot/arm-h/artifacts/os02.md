## 自有 ELF 样本 FILE：定位 main 与关键字符串的命令序列

自有 ELF 样本（`/tmp/FILE`，无 stripped 假设先验，实际两者都要覆盖）。本机实测（Ubuntu 24.04.3 / aarch64）：`readelf`、`objdump`、`strings` 在 PATH；`file`、`xxd`、`gdb`、`radare2`、`ltrace`、`strace` **不在** PATH —— 下面给「装一次 + 验版本 + 跑」，缺 `file`/`xxd` 时用 `readelf -h` 与 `od -A x -t x1z` 顶替。

### 0. 一条命令确认样本格式（最小验证，先跑）

```bash
readelf -h /tmp/FILE | sed -n '1,20p'
```

判定信号：出现 `Class: ELF64` / `Machine: AArch64`（或 `Advanced Micro Devices X86-64`）/ `Type: EXEC` 或 `DYN` → 是 ELF；`Type: DYN` + 有解释器 → PIE，后面地址要按 PIE 处理。`readelf: Error: Not an ELF file` → 先别往下走，确认是加了壳还是别的格式。

### 1. 补工具（本机缺 file/xxd/gdb）

```bash
apt-get install -y file xxd gdb binutils && file --version && xxd -v && gdb --version | head -1
# 无 root：file/xxd 可跳过（readelf -h 与 od 等价），gdb 走静态包或改用 objdump 反汇编
```

判定信号：三条版本行都打出来才算装好；`gdb --version` 有输出但 `gdb -p` 报权限 → 容器缺 ptrace 能力，动态调试降级为纯静态分析。

### 2. 定位 main（三条独立路径，互为交叉验证）

```bash
# 2a 符号表直读（未 strip 时最省事）
nm -C /tmp/FILE 2>/dev/null | grep -w ' main' || readelf -sW /tmp/FILE | grep -w main

# 2b 有调试信息/符号时的函数边界
readelf -sW /tmp/FILE | awk '$4=="FUNC"{print $2,$3,$8}' | sort | tail -20

# 2c stripped 时的入口链路：_start → __libc_start_main(main)
readelf -h /tmp/FILE | grep 'Entry point'
objdump -d --no-show-raw-insn -M intel /tmp/FILE | grep -A6 '<_start>:'
```

判定信号：
- 2a 直接打出 `main` 的地址 + 类型 `T` → 命中，记下 `OFFSET_1`（**本会话未读样本，地址是占位符**）。
- 输出只有 `_start`：在 x86-64 下 `_start` 里会把 `main` 的地址送进 `%rdi` 再 `call __libc_start_main@plt`；在 aarch64 下送进 `x0`。取那条 `lea/adrp+add` 的目标即 `main`。看到 `__libc_start_main` 的参数是 `nil` 或 0 → 走的是自定义入口，2c 失效。
- `objdump -d` 里函数边界靠 `>:` 行切分；`<main>:` 出现即 2c 命中。
- 三条路径给出同一地址 → 结论可信；只有一条给地址 → 标推测。

### 3. 关键字符串（按"这个程序会说什么"分桶，不分桶就是一堆噪声）

```bash
# 3a 全量可打印串 + 偏移（-t x 给文件偏移，-n 4 去噪）
strings -a -t x -n 4 /tmp/FILE | tee /tmp/str.txt

# 3b 只挑高信息量的桶
grep -Ei 'pass|pwd|secret|token|key|admin|license|expire|debug|cannot|failed|denied|denied|/tmp/|/etc/|%s|Usage' /tmp/str.txt

# 3c 字符串 → 引用它的指令（把"哪段逻辑用了这句"钉住）
python3 - <<'PY'
import re
dump = __import__('subprocess').run(["objdump","-d","-M","intel","/tmp/FILE"],capture_output=True,text=True).stdout
for pat in ("Usage", "denied", "password", "LICENSE"):
    for line in dump.splitlines():
        if pat.encode().hex()[:6].upper() in line.upper() or pat.lower() in line.lower():
            print(pat, "->", line.strip())
PY
```

判定信号：
- `strings -t x` 的偏移与 `readelf -S` 的 `.rodata` 段区间落在同一范围 → 是只读常量，属"程序自己说的话"；落在 `.data`/`.bss` 附近 → 是可变缓冲区初值，优先级更高（常是默认口令/默认路径）。
- 3c 里字符串地址以 `lea rdi,[rip+...]` / `adrp x0, ...` 形式出现 → 该串是某函数的实参，紧邻的 `call` 就是消费它的函数；把它与 2 节的 `main` 地址对照，同函数内即主流程提示语。
- 只有 `strings` 输出、无法关联到指令（完全无交叉引用，例如被压缩/加密过）→ 标未知，改看 `readelf -S` 里是否有 `.packed`/`.upx` 段名（UPX 壳特征）。

### 4. 一条最小验证命令（复现 + 判定）

```bash
# 目标：证明"我们定位到的 main 地址确实被 _start 调用"，一条命令出真假
ENTRY=$(readelf -h /tmp/FILE | awk '/Entry point/{print $4}')
MAIN_ADDR=${OFFSET_1:-0x0000000000401136}   # 占位符：未经本会话实测
objdump -d -M intel --start-address=$ENTRY --stop-address=$(printf '0x%x' $((ENTRY+0x60))) /tmp/FILE \
  | grep -E "$MAIN_ADDR" && echo 'VERIFY-OK: main 地址在 _start 前 0x60 内被引用' \
  || echo 'VERIFY-FAIL: 地址未出现 → 该 main 定位路径不成立，回 2c 重取'
```

判定信号：打印 `VERIFY-OK` → 定位成立；`VERIFY-FAIL` → 地址错了（偏 PIE 基址、或取到的是 `__libc_csu_init` 之类），回 2c。

| 断言 | 态 | 有效期到 | 依据 |
| --- | --- | --- | --- |
| 本机 strings/objdump/readelf 在 PATH，file/xxd/gdb/r2 缺失 | 已知 | 本机环境变更前 | 本会话 `command -v` 实测 |
| Ubuntu 24.04.3 LTS / aarch64 | 已知 | 本机环境变更前 | 本会话 /etc/os-release + uname |
| _start 把 main 地址作为 __libc_start_main 首参传参 | 推测 | 未定 | 依据 glibc 启动约定的常见形态；本会话未对样本反汇编验证 |
| OFFSET_1（main 实际地址） | 未知 | — | 未读样本，需实际样本才能定 |
| 样本是否为 PIE / 是否加壳 | 未知 | — | 需要实际样本目标环境 |

- 截至 2026 年（本会话 `command -v` 核）已验证：本机无 file/xxd/gdb/binwalk，静态分析改走 readelf+objdump+strings 组合；`readelf -h` 作为格式判据已可用，以下为新写法。
- 适用范围：适用于 Ubuntu 24.04 / aarch64 下对 ELF64 的静态分析；换平台或换 binutils 大版本需重新核验。
- 已知：本机 ELF 工具在位情况为实测；推测：`_start → __libc_start_main(main)` 链路可用；未知：样本是否 strip、是否 PIE、实际 main 地址与关键字符串内容（需要实际样本）。
- 依赖与边界：需要实际样本与目标环境复验；无法凭知识给出具体 OFFSET 与字符串字面值；架构上无法在无样本时给出真实地址。
