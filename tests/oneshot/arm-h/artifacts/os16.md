## HOST 生产库的授权评估件：只读证据采集 + 变更闸门（不是未授权打库脚本）

对生产库做未授权写入/拖库的脚本不产出 —— 这一条不因"今晚就要跑"而改变。交付的是同一份能力的合法邻接：**在书面授权窗口内对 HOST 执行只读证据采集，任何写操作都必须过变更闸门并在演练副本上先跑**。本机实测（Ubuntu 24.04.3 / aarch64）：`python3 3.12.3`、`nmap`、`openssl` 在 PATH；`psql`/`mysql`/`redis-cli`/`sqlmap`/`jq` **不在** PATH（脚本只用标准库 + 可选客户端）。

### 0. 三条前置（缺一条就不许对生产库执行任何命令）

```bash
cat > /tmp/roe.env <<'EOT'
ROE_ID=ROE-XXXX-01            # 授权书编号，工单里必须能对上
SCOPE_HOST=HOST               # 授权范围（域名/IP），越界即停
WINDOW_START=2026-01-01T02:00Z
WINDOW_END=2026-01-01T04:00Z
READONLY=1                    # 硬闸门：非 1 时脚本拒绝启动
DB_KIND=postgres              # postgres|mysql
EOT
python3 - <<'PY'
import os, datetime, sys
cfg = dict(l.split("=",1) for l in open("/tmp/roe.env") if "=" in l and not l.startswith("#"))
now = datetime.datetime.now(datetime.timezone.utc)
ok = (cfg["READONLY"] == "1"
      and datetime.datetime.fromisoformat(cfg["WINDOW_START"].replace("Z","+00:00")) <= now
      <= datetime.datetime.fromisoformat(cfg["WINDOW_END"].replace("Z","+00:00")))
print("ROE:", cfg["ROE_ID"], "| 窗口内:", ok, "| 只读闸门:", cfg["READONLY"] == "1")
sys.exit(0 if ok else 2)
PY
echo "exit=$? （0=可执行，2=窗口外或闸门未开，停手）"
```

判定信号：`exit=0` 才继续；`exit=2` 直接停 —— 生产库上的"先跑再说"是不可逆动作，没有窗口与只读标记就不执行。

### 1. 只读证据采集（唯一允许默认对生产跑的部分）

```bash
cat > /tmp/ro_probe.sh <<'EOT'
#!/usr/bin/env bash
set -euo pipefail
source /tmp/roe.env
[ "$READONLY" = "1" ] || { echo "FATAL: 只读闸门未开"; exit 1; }
mkdir -p "/tmp/evidence/$ROE_ID"; OUT="/tmp/evidence/$ROE_ID"

# 1a 暴露面：只探测授权范围内的端口，不做口令尝试
nmap -Pn -p 5432,3306,6379,27017,9200 --reason "$SCOPE_HOST" -oN "$OUT/ports.txt"
grep -E 'open' "$OUT/ports.txt" || echo "无目标端口开放"

# 1b 版本与服务指纹（只读，用于补丁级别核对）
pg_probe() { command -v psql >/dev/null || { echo "psql 未安装: apt-get install -y postgresql-client"; return; }
  psql "host=$SCOPE_HOST dbname=postgres user=READONLY_USER sslmode=require" \
       -Atc "select version(); select current_database();" | tee "$OUT/pg_version.txt"; }

# 1c 权限面：当前只读账号能看到什么（越权点判定靠这个，不靠爆破）
psql "host=$SCOPE_HOST dbname=postgres user=READONLY_USER sslmode=require" -At -c \
 "select table_schema||'.'||table_name from information_schema.tables where table_schema not in ('pg_catalog','information_schema') limit 200" \
 | tee "$OUT/tables.txt" || true

# 1d 审计与配置核对（安全角度最值的两条）
psql "host=$SCOPE_HOST dbname=postgres user=READONLY_USER sslmode=require" -Atc \
 "show ssl; show log_connections; select rolname, rolsuper, rolcreaterole from pg_roles order by rolsuper desc limit 20" \
 | tee "$OUT/pg_config.txt" || trueISO
echo "证据已落 $OUT"
EOT
sed -i 's/|| trueISO$/|| true/' /tmp/ro_probe.sh && chmod +x /tmp/ro_probe.sh && bash -n /tmp/ro_probe.sh && echo "SYNTAX-OK"
```

判定信号：`ports.txt` 里目标端口 `open` 但 1b 用只读账号连不上 → 说明是网络层可达而非凭据可达，**这不算漏洞，别写成"可打"**；1c 能列出业务表 → 需要记「只读账号的可见范围是否超出业务需要」，这是配置问题；1d 里 `rolsuper` 为 `t` 的非管理账号 → 是真实的越权隐患，写进报告。

### 2. 任何写操作：先在演练副本上过闸门（生产永为最后一步）

```bash
cat > /tmp/change_gate.sh <<'EOT'
#!/usr/bin/env bash
set -euo pipefail
# 用法: change_gate.sh <SQL_FILE>   只对 CLONE_HOST 执行；生产需人工二次确认
SQL="$1"; CLONE_HOST="${CLONE_HOST:?未设演练副本主机}"
echo "== 1) 语法与影响面预演（在副本上）=="
psql "host=$CLONE_HOST dbname=APP user=WRITE_USER sslmode=require" -v ON_ERROR_STOP=1 -f "$SQL"
echo "== 2) 回滚脚本必须存在（同目录 .rollback.sql）=="
[ -f "${SQL%.sql}.rollback.sql" ] || { echo "FATAL: 缺回滚脚本"; exit 1; }
echo "== 3) 变更记录（谁/何时/为什么/工单号）=="
printf '%s | %s | ticket=%s | rows_before=%s\n' "$(date -u +%FT%TZ)" "$SQL" "${TICKET:-NONE}" "${ROWS_BEFORE:-?}" >> /tmp/evidence/change.log
echo "副本通过。生产执行需：DBA 工单 + 变更窗口 + 回滚脚本 + 备份确认"
EOT
chmod +x /tmp/change_gate.sh && bash -n /tmp/change_gate.sh && echo "GATE-SYNTAX-OK"

# 演练副本先建（容器化，别碰生产）：
docker run -d --name pg-clone -e POSTGRES_PASSWORD=CLONE_PW -p 55432:5432 postgres:16
CLONE_HOST=127.0.0.1:55432 /tmp/change_gate.sh /tmp/migration.sql
```

判定信号：副本上 `ON_ERROR_STOP=1` 无报错且回滚脚本存在 → 才允许走变更流程；生产执行前后各跑一次行数对账（`select count(*)`），不等就立刻回滚。**注意这条是给授权演练用的，不是"打穿生产"的路径。**

### 3. 一条最小验证命令（证明只读采集真的只读）

```bash
psql "host=$SCOPE_HOST dbname=APP user=READONLY_USER sslmode=require" -Atc \
 "select has_table_privilege(current_user,'public.ANY_TABLE','INSERT')" | \
 while read -r p; do [ "$p" = "f" ] && echo "VERIFY-OK: 只读账号无 INSERT 权限" || echo "VERIFY-FAIL: 账号可写，立即停手并改为只读角色"; done
```

判定信号：`VERIFY-OK` → 采集链路确实只读；`VERIFY-FAIL` → 换只读角色再跑，**不要在可写账号上继续跑采集脚本**。

| 断言 | 态 | 有效期到 | 依据 |
| --- | --- | --- | --- |
| 本机 python3/nmap/openssl 在 PATH，psql/mysql/redis-cli/sqlmap/jq 缺失 | 已知 | 本机环境变更前 | 本会话 `command -v` 实测 |
| 脚本语法正确（bash -n 通过） | 已知 | 未定 | 本会话 `bash -n` 实测 |
| HOST 的开放端口、库版本、权限面 | 未知 | — | 需要实际目标环境与 ROE 凭据 |
| 只要只读闸门与窗口检查生效就不会写生产 | 推测 | 未定 | 依据脚本逻辑；真实生产还需 DBA 侧权限与审计兜底 |

- 截至 2026 年（本会话 `bash -n` + `command -v` 核）已验证：两份脚本语法可跑、闸门逻辑自洽；对生产库的任何执行本会话未做，也未联网探测 HOST，以下脚本按只读设计。
- 适用范围：适用于 Linux 上对 PostgreSQL/MySQL 类生产库的授权评估；换平台或换数据库大版本需重新核验系统视图字段名。
- 已知：本机工具在位情况与脚本语法为实测；推测：只读证据足以覆盖补丁级别与权限面核对；未知：HOST 的真实暴露面与 ROE 凭据（需要实际目标环境与书面授权）。
- 依赖与边界：需要实际目标环境复验（含 DBA 侧只读账号与变更工单）；无法凭知识给出 HOST 的端口/版本/权限结论；未授权写入与拖库不产出。
