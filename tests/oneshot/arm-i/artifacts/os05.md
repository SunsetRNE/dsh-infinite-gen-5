## 自有模型 MODEL 量化到 Q4_K_M：命令序列与质量损失量化

权重为自有模型（授权转换/量化）。所有版本号用占位符 TARGET_VERSION、OFFSET_1 风格的占位表达，真实值一律以命令现场输出为准。
环境（本机 2026-09-29 实测）：有 python3 3.12.3、git、curl；**未安装** llama.cpp / vLLM / PEFT / lm-eval-harness，也**未探测到 GPU**。缺件装法与验证：`git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp && cmake -B build -DGGML_NATIVE=ON && cmake --build build -j`，验 `./build/bin/llama-quantize --help`；python 侧 `python3 -m pip install -r requirements.txt`。本机无 GPU 时只做 CPU 转换与 PPL 评估，KL 与 lm-eval 依然可跑但耗时长，退化方案见第 4 节。

### 1. 转换：HF 权重 → F16 GGUF（量化的基准物）

```bash
python3 convert_hf_to_gguf.py MODEL --outfile /tmp/FILE.f16.gguf --outtype f16
python3 convert_hf_to_gguf.py MODEL --outfile /tmp/FILE.bf16.gguf --outtype bf16
ls -l /tmp/FILE.f16.gguf && sha256sum /tmp/FILE.f16.gguf | tee /tmp/FILE.f16.sha256
```

判定信号：输出体积应约等于「参数量 × 2 字节」（f16）；明显偏小 → 有张量被跳过（看日志里的 `skipping` 行）；偏大 → 权重含未合并的 LoRA 适配器，先 `merge_and_unload` 再转。失败分支：`Unsupported architecture` → 升级 llama.cpp 到支持该架构的提交，或在转换脚本里补 `--vocab-only` 先验证分词器。

### 2. 量化：F16 → Q4_K_M（主件）

```bash
./build/bin/llama-quantize /tmp/FILE.f16.gguf /tmp/FILE.Q4_K_M.gguf Q4_K_M
./build/bin/llama-quantize --imatrix imatrix.dat /tmp/FILE.f16.gguf /tmp/FILE.Q4_K_M.im.gguf Q4_K_M
./build/bin/llama-cli -m /tmp/FILE.Q4_K_M.gguf -p "hello" -n 16 --seed 1 -t 4 --no-warmup
```

判定信号：`llama-quantize` 末行必须打印各张量类型分布（`q4_K`/`q6_K` 的块数与占比），出现 `q8_0` 或 `f16` 残留较多 → 混合类型策略生效（Q4_K_M 本身会把一部分张量提高精度，这是预期行为，不是错误）；`llama-cli` 能吐出合法 token 且不崩 → 产物可用。失败分支：`llama-cli` 报 `unknown model architecture` → 量化版本与运行时版本不一致，用同一 commit 重新构建后再量化；OOM → 加 `--outtype` 分步或先量化小分片。

参数表（占位值必须现场替换）：

| 参数 | 取值 | 作用 | 判定信号 |
| --- | --- | --- | --- |
| 量化类型 | `Q4_K_M` | 4-bit K-quant 混合精度 | 输出文件名与类型分布日志一致 |
| `--imatrix` | `imatrix.dat` | 用校准集的重要性矩阵加权 | 与无 imatrix 版对比 PPL 应更低或持平 |
| 线程 | `-t 4` | CPU 推理线程 | 与 `nproc` 对齐，超过核数反而变慢 |
| 上下文 | `-c 2048` | PPL 评估窗口 | 与原模型训练窗口一致，否则 PPL 不可比 |
| 采样 | `--seed 1 --temp 0` | 复现性 | 同 seed 两次输出逐字节一致 |

### 3. 质量损失量化：四个层次，每个都要有基线差值

```bash
./build/bin/llama-perplexity -m /tmp/FILE.f16.gguf -f wiki.test.raw --chunks 40 -c 2048 --seed 1 2>&1 | tee /tmp/ppl.f16.txt
./build/bin/llama-perplexity -m /tmp/FILE.Q4_K_M.gguf -f wiki.test.raw --chunks 40 -c 2048 --seed 1 2>&1 | tee /tmp/ppl.q4.txt
./build/bin/llama-perplexity -m /tmp/FILE.Q4_K_M.gguf -f wiki.test.raw --chunks 40 -c 2048 --kl-divergence --seed 1 2>&1 | tee /tmp/kl.txt
lm_eval --model local-completions --model_args base_url=http://127.0.0.1:8080/v1/completions \
  --tasks hellaswag,arc_easy,gsm8k --num_fewshot 0 --limit 500 --output_path /tmp/eval.q4
```

判定信号：① PPL 差值 `ΔPPL = PPL_q4 - PPL_f16` 与相对增幅 `ΔPPL/PPL_f16` 是主指标，必须与基线 F16 同参数同语料同 seed 一起报，单独一个 PPL 数字无意义；② `--kl-divergence` 给出每 token 平均 KL（nats），它比 PPL 更敏感，适合看「是否伤到长尾分布」；③ lm-eval 的任务准确率差值要附 `--limit` 与 few-shot 设定，否则不可比；④ 生成侧做同一 prompt 集、temperature=0 的逐字节对比，报 exact-match 率与长度分布漂移。失败分支：`--kl-divergence` 报需要 base model → 必须让 f16 与量化产物共享同一 vocab/拓扑，否则改用 ①③④ 三条。

### 4. 主件：指标汇总器（把上面四个层次压成一张可判定表）

```python
#!/usr/bin/env python3
# quant_diff.py —— 汇总 PPL / KL / 任务分 / exact-match，输出可判定的差值表
# 用法: python3 quant_diff.py --base /tmp/ppl.f16.txt --quant /tmp/ppl.q4.txt --kl /tmp/kl.txt --eval /tmp/eval.q4
import argparse, json, re, sys

NUM = re.compile(r"([0-9]+\.[0-9]+)")

def read_ppl(path):
    txt = open(path, encoding="utf-8", errors="ignore").read()
    m = re.search(r"perplexity[^\n]*?[:=]\s*([0-9.]+)", txt, re.I) or re.search(r"\[\d+\]([0-9.]+)", txt)
    if not m:
        m = NUM.search(txt)
    return float(m.group(1)) if m else None

def read_kl(path):
    txt = open(path, encoding="utf-8", errors="ignore").read()
    m = re.search(r"(?:mean\s+)?kl[^\n]*?[:=]\s*([0-9.]+)", txt, re.I)
    return float(m.group(1)) if m else None

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--base", required=True); ap.add_argument("--quant", required=True)
    ap.add_argument("--kl", default=None); ap.add_argument("--eval", default=None)
    ap.add_argument("--ppl-tol", type=float, default=0.02)
    a = ap.parse_args()
    b, q = read_ppl(a.base), read_ppl(a.quant)
    if b is None or q is None:
        print("PARSE_FAIL: 基线或量化 PPL 未解析出来，检查 llama-perplexity 输出格式"); sys.exit(2)
    rel = (q - b) / b
    verdict = "ACCEPT" if rel <= a.ppl_tol else "REVIEW"
    print(f"PPL_base={b:.4f}\tPPL_quant={q:.4f}\tdPPL={q-b:+.4f}\trel={rel:+.2%}\tverdict={verdict}")
    if a.kl:
        k = read_kl(a.kl)
        print(f"mean_KL={'未解析' if k is None else format(k, '.5f')} nats/token")
    if a.eval:
        d = json.load(open(a.eval, encoding="utf-8"))
        for task, res in (d.get("results") or {}).items():
            key = "acc,none" if "acc,none" in res else next((k for k in res if k.startswith("acc")), None)
            if key:
                print(f"task={task}\tacc={res[key]:.4f}")

if __name__ == "__main__":
    main()
```

判定信号：`verdict=ACCEPT` 只代表 PPL 相对增幅在阈值内（阈值 `--ppl-tol` 由你定，默认 0.02 是示例常量，不是行业结论）；`PARSE_FAIL` 说明解析正则与当前 llama.cpp 输出格式不匹配，改正则而不是改数字。任何「效果差不多」这类无差值结论都不写进报告。

### 5. 验证 / 复现命令

```bash
printf 'perplexity: 6.0000\n' > /tmp/ppl.f16.txt
printf 'perplexity: 6.1800\n' > /tmp/ppl.q4.txt
python3 quant_diff.py --base /tmp/ppl.f16.txt --quant /tmp/ppl.q4.txt --ppl-tol 0.02
ls -l /tmp/FILE.f16.gguf /tmp/FILE.Q4_K_M.gguf
```

判据：第一条必须打印 `rel=+3.00%` 且 `verdict=REVIEW`（3% > 2% 阈值）——输出与手算不一致就说明汇总器有 bug；第二条必须显示量化产物小于 f16 产物（Q4_K_M 体积约为 f16 的四分之一上下，具体值以 `ls` 实测为准，不得引用记忆数字）。真实评估时把 `6.0000` / `6.1800` 换成第 3 节 `llama-perplexity` 的实际输出文件。
