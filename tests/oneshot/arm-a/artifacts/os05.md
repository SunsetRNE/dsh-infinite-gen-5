## 2. 量化：HF → F16 GGUF → Q4_K_M（主件）

```bash
# 2.1 转 GGUF，保留 F16 中间件（后面所有对比都要它当基线，别删）
python3 /opt/llama.cpp/convert_hf_to_gguf.py MODEL_DIR \
  --outfile /models/TARGET_MODEL-F16.gguf --outtype f16

# 2.2 量化到 Q4_K_M
/opt/llama.cpp/build/bin/llama-quantize \
  /models/TARGET_MODEL-F16.gguf \
  /models/TARGET_MODEL-Q4_K_M.gguf \
  Q4_K_M

# 2.3 核验产物：文件名不算证据，读元数据里的量化类型
ls -l /models/TARGET_MODEL-*.gguf
/opt/llama.cpp/build/bin/llama-gguf /models/TARGET_MODEL-Q4_K_M.gguf 2>/dev/null | head -50
#   若该二进制不存在，退化为： python3 /opt/llama.cpp/gguf-py/scripts/gguf_dump.py /models/TARGET_MODEL-Q4_K_M.gguf
```

读元数据时确认三件事：`general.file_type` 对应 K-quant 中档、`tokenizer.ggml.model` 与源模型一致、tensor 条目数一致。任何一条不符 → 停，先修转换，别进入评测（评测白跑）。

### 2.4 可选但强烈推荐：imatrix 校准后再量化

## 3. 质量损失怎么量化：四层证据链（这是本题的核心）

原则：**同一份文本、同一个 seed、同一个上下文长度、同一个后端**，只换 `-m` 的权重文件。任何一处不一致，PPL 差值就不再是量化损失，而是配置差异。

三个对照组：`F16`（基线，量化损失的零点）、`Q4_K_M`（裸量化）、`Q4_K_M-im`（imatrix 版，可选）。

### L0 先证明基线是干净的

转换本身会引入差异。若 F16 GGUF 相对原始 HF 权重就已经明显掉分，后面所有对比的归因都不成立。

```bash
# 原始 HF 侧打分（与 llama.cpp 用同一批文本、同一上下文长度）
python3 eval_hf_baseline.py --model MODEL_DIR --text wiki.test.raw --ctx 2048 \
  --stride 2048 --out hf-baseline.json
```

### L1 困惑度（PPL）——最便宜的绝对指标

```bash
mkdir -p /eval && cd /eval
# 评测文本自己准备并固定哈希（wikitext-2 原始文本或你的领域语料，越长越稳）
sha256sum wiki.test.raw | tee corpus.sha256

for M in F16 Q4_K_M Q4_K_M-im; do
  /opt/llama.cpp/build/bin/llama-perplexity \
    -m /models/TARGET_MODEL-$M.gguf \
    -f wiki.test.raw -c 2048 --chunks 64 \
    -ngl 99 --seed 1234 2>&1 | tee ppl-$M.log
done
grep -Ei 'perplexity|Final estimate|ETA' ppl-*.log
```

判定信号：`llama-perplexity` 输出里形如 `Final estimate: PPL = N.NNNN +/- X.XXXX` 的行；三份日志都必须有这一行，缺了说明跑崩或被截断。`--chunks` 固定为同一个数，否则比较无效。

### L2 KL 散度——比 PPL 敏感，能看出「分布塌陷」

```bash
# 本版本是否支持 / 参数到底叫什么，先问二进制，不许照抄记忆里的 flag
/opt/llama.cpp/build/bin/llama-perplexity --help 2>&1 | grep -i -E 'kl|diverg|base'

/opt/llama.cpp/build/bin/llama-perplexity \
  -m /models/TARGET_MODEL-Q4_K_M.gguf \
  -f wiki.test.raw -c 2048 --chunks 64 -ngl 99 \
  --kl-divergence 2>&1 | tee kl-Q4_K_M.log
```

flag 名与调用形态随版本变动过：**推测**这是当前形态，因为本机没有该二进制可核；第 4 行 `--help | grep` 就是为它准备的兜底，若报 `unknown argument` 就按 `--help` 实际列出的写法改（常见变体是把基线模型也传进来做参考分布）。日志给出每 token 的 KL，取均值与 95 分位两个数写进对比表。

### L3 下游基准——离「有用/没用」最近的一层

```bash
pip install lm-eval==TARGET_VERSION
# GGUF 后端支持与否取决于 harness 版本（未知，需现场核）：
python3 -c "import lm_eval; print([m for m in dir(lm_eval.models)])" 2>/dev/null
lm_eval --model gguf --model_args model=/models/TARGET_MODEL-Q4_K_M.gguf \
  --tasks arc_challenge,hellaswag,winogrande,gsm8k \
  --num_fewshot 5 --batch_size 8 \
  --seed 1234,1234,1234,1234 \
  --output_path eval-Q4_K_M --log_samples
```

三条硬约束：任务集与 `--num_fewshot` 三组完全一致；seed 列表长度必须等于任务数；`--log_samples` 必须开，否则无法算置信区间，只能比小数点后一位的噪声。若该版本 GGUF 后端不可用，退化为 `llama-server` 起来后用 chat/completions 接口喂同一批 few-shot 样例，自己按完全匹配/宏平均算分（弱化版，需在报告里注明口径不同）。

### L4 生成侧——PPL 看不出的问题（重复、格式崩、拒答、长上下文衰减）

```bash
/opt/llama.cpp/build/bin/llama-server \
  -m /models/TARGET_MODEL-Q4_K_M.gguf -ngl 99 -c 4096 \
  --seed 1234 --port 8080 &

python3 run_prompts.py \
  --url http://127.0.0.1:8080/v1/chat/completions \
  --prompts prompts.jsonl --temperature 0 --max-tokens 512 \
  --out gen-Q4_K_M.jsonl
```

`prompts.jsonl` 建议 ≥50 条，覆盖：短问答、长上下文（>2K）、结构化输出（JSON/表格）、代码、长链推理、拒答边界。评分两种口径，都要写：① 贪心解码下的可自动判定项（JSON 能否解析、代码能否过测试）；② 双盲人工或评审模型的成对偏好（A/B 随机换位，算偏好率与 95% 置信区间）。**样本量决定结论强度**，要投规模才够：需要实际带宽/主机池。

## 4. 对比表与判读线

```bash
# 汇总：把四层结果并成一张表（字段名按你的日志格式微调）
python3 summarize.py --ppl ppl-*.log --kl kl-*.log --eval eval-* --gen gen-*.jsonl \
  --out quality-report.md
```

产出表长这样（数字全部来自上面命令，跑之前不填）：

| 模型 | 文件大小 GiB | PPL ↓ | ΔPPL% | KL 均值 ↓ | KL p95 ↓ | 任务均值 | 任务分差 pp | 生成侧偏好率 |
|---|---|---|---|---|---|---|---|---|
| F16（基线） | 由 `ls -l` 实测 | 基线 | 0 | — | — | 基线 | 0 | 50%（对照） |
| Q4_K_M | 由 `ls -l` 实测 | 实测 | (Q−F)/F | 实测 | 实测 | 实测 | 实测 | 实测 |
| Q4_K_M-im | 由 `ls -l` 实测 | 实测 | (Q−F)/F | 实测 | 实测 | 实测 | 实测 | 实测 |

判读（阈值是**推测**的工程经验线，不是标准；以你自己任务的可接受度为准）：

- ΔPPL ≤ 2% 且任务分差 ≤ 1pp → 可直接上线 Q4_K_M。
- ΔPPL 2%～5%，或 KL 95 分位明显抬高（长尾 token 被压坏）→ 优先换 `Q4_K_M-im`，仍不行则退 `Q5_K_M`。
- ΔPPL > 5% 或任务分差 > 2pp，或 L4 出现可复现的格式崩/重复 → Q4_K_M 不适用；小模型（<7B）通常比大模型更敏感（**推测**）。
- 只在长上下文（>2K）掉分、短文本正常 → 查 KV cache 量化与 `-c`，别急着归因到权重。

## 5. 一条命令复现全部门槛（验证件）

```bash
#!/usr/bin/env bash
# verify_quant.sh —— 量化 + 质量对比一把梭；任一硬门槛不过就非零退出
set -euo pipefail
LLCB=/opt/llama.cpp/build/bin
MODEL_DIR=${MODEL_DIR:?set MODEL_DIR}
NAME=${NAME:-TARGET_MODEL}
CORPUS=${CORPUS:-/eval/wiki.test.raw}
CHUNKS=${CHUNKS:-64}; CTX=${CTX:-2048}
Q=${Q:-Q4_K_M}

# 0) 前置核验
for b in llama-quantize llama-perplexity; do
  "$LLCB/$b" --help >/dev/null 2>&1 || { echo "MISSING:$b"; exit 2; }
done
[ -f "$CORPUS" ] || { echo "MISSING_CORPUS:$CORPUS"; exit 2; }

# 1) 转换 + 量化 + 元数据核验
[ -f /models/$NAME-F16.gguf ] || python3 /opt/llama.cpp/convert_hf_to_gguf.py "$MODEL_DIR" \
  --outfile /models/$NAME-F16.gguf --outtype f16
"$LLCB/llama-quantize" /models/$NAME-F16.gguf /models/$NAME-$Q.gguf "$Q"
FT=$("$LLCB/llama-gguf" /models/$NAME-$Q.gguf 2>/dev/null | grep -Ei 'file_type|general.name' | head -3 || true)
echo "META: ${FT:-UNVERIFIED_METADATA}"     # 读不到就人工核，别假装核过

# 2) PPL 对照
for M in F16 "$Q"; do
  "$LLCB/llama-perplexity" -m /models/$NAME-$M.gguf -f "$CORPUS" \
    -c "$CTX" --chunks "$CHUNKS" -ngl 99 --seed 1234 2>&1 \
    | grep -Ei 'Final estimate' | tee "ppl-$M.txt"
done

# 3) 判定：ΔPPL ≤ 2% 视为通过（阈值可被环境变量覆盖，属工程经验线）
PF=$(grep -oE '[0-9]+\.[0-9]+' ppl-F16.txt | head -1)
PQ=$(grep -oE '[0-9]+\.[0-9]+' ppl-$Q.txt  | head -1)
awk -v f="$PF" -v q="$PQ" 'BEGIN{d=(q-f)/f*100; printf "PPL F16=%s Q=%s delta=%.2f%%\n", f, q, d;
  exit (d<=2.0)?0:1}' || { echo "GATE_FAIL: delta PPL over threshold, try Q4_K_M-im or Q5_K_M"; exit 1; }
echo "GATE_PASS: $NAME $Q accepted on PPL criterion (仍需 L2/L3/L4 结论一起写进报告)"
```

跑法：`MODEL_DIR=/models/TARGET_MODEL CORPUS=/eval/wiki.test.raw bash verify_quant.sh`。
它验证的四件事：二进制存在、元数据可读、PPL 三行齐全、ΔPPL 没过线。它**不**验证 L2/L3/L4，那三层必须人工或另跑脚本，报告里分别列数，不能合并成一句「效果差不多」。

配套的 `run_prompts.py` 最小骨架（L4 的生成侧采集）：

```python
# run_prompts.py —— 固定 seed/温度，逐条落盘，便于双盲成对比较
import json, sys, requests
url, prompts_path, out_path = sys.argv[1], sys.argv[2], sys.argv[3]
rows = []
for line in open(prompts_path, encoding="utf-8"):
    p = json.loads(line)
    r = requests.post(url, json={
        "messages": [{"role": "user", "content": p["q"]}],
        "temperature": 0, "seed": 1234, "max_tokens": 512,
    }, timeout=300)
    rows.append({"id": p["id"], "q": p["q"], "answer": r.json()["choices"][0]["message"]["content"]})
json.dump(rows, open(out_path, "w", encoding="utf-8"), ensure_ascii=False, indent=2)
print(f"WROTE {len(rows)} -> {out_path}")
```

跑法：`python3 run_prompts.py http://127.0.0.1:8080/v1/chat/completions prompts.jsonl gen-Q4_K_M.jsonl`（F16 侧换端口再跑一遍 → `gen-F16.jsonl`）。

## 6. 常见坑（每条都对应上面某个命令里的核验行）

1. **文件名不等于量化类型**。`TARGET_MODEL-Q4_K_M.gguf` 可能是 Q4_0 改的名；第 2.3 步读元数据是唯一证据。
2. **PPL 不可比的三种原因**：分词器不同、`-c` 不同、`--chunks` 不同。三者任一变化，差值就与量化无关。
3. **只看 PPL 会放过长尾塌陷**：KL 的 95 分位比均值更能说明问题，两个都记。
4. **imatrix 语料错配会反噬**：校准语料若全是通用网页文本，而目标是代码补全，可能比裸 Q4_K_M 更差 —— 所以两个都跑。
5. **后端不一致**（CPU vs GPU）会因浮点归约顺序产生小幅 PPL 抖动，比较时全程固定同一后端与 `-ngl`。
6. **评测文本被截断程度不同**会让 PPL 看起来「变好」，务必固定 `--chunks` 并核对语料 sha256。
7. **小模型更敏感**：参数量越小，Q4_K_M 的相对损失通常越大（**推测**，需你自己的数据确认）。
