# 栈溢出利用 (Stack Exploit)

## 概述

栈溢出（Stack Overflow）是 PWN 中最基础也是最经典的漏洞利用技术。当程序向栈缓冲区写入的数据量超过缓冲区本身的容量时，多余的数据会覆盖栈上相邻的数据区域，包括局部变量、EBP/RBP（基址指针）、返回地址、函数参数等。通过精确控制这些被覆盖的值，攻击者可以劫持程序的执行流程。

栈溢出利用技术经过了数十年的发展，从早期简单的 Ret2text 到现代复杂的 ROP、SROP、dl_resolve 等，虽然在现代编译器保护下直接利用的难度不断增大，但仍然是每一位 PWN 选手必须掌握的基石技能。

## 常见攻击/分析手法

### 1. Ret2text (Return to Text)
- **原理**: 将函数的返回地址覆盖为程序自身代码段（.text 段）中已有的危险函数或指令序列，如后门函数（backdoor）、`system("/bin/sh")` 调用等。
- **条件**: 程序中有可直接使用的危险函数或指令序列。
- **对抗 PIE**: 需要先泄露程序基址，或在低 12 位固定偏移的情况下进行部分覆盖爆破。
- **简单示例**: 程序内定义了 `win()` 函数直接输出 flag，只需覆盖返回地址为其入口地址。

### 2. Ret2shellcode (Return to Shellcode)
- **原理**: 在栈上布置 Shellcode（一段执行恶意功能的机器码），然后将返回地址覆盖为 Shellcode 的起始地址。
- **条件**: 栈必须具有可执行权限（NX 关闭），或通过 mprotect 等方式动态赋予栈可执行权限。
- **挑战**: 需要知道 Shellcode 在栈上的精确地址，通常结合 JMP ESP 指令（x86）或借助 `jmp rsp` gadget（x64）间接跳转。
- **Shellcode 构建**: 通常以 execve("/bin/sh", NULL, NULL) 为目标，需要避免空字节。

### 3. Ret2syscall (Return to Syscall)
- **原理**: 通过 ROP 链分别设置系统调用号（rax）、参数寄存器（rdi/rsi/rdx 等），然后调用 syscall 指令实现 `execve("/bin/sh")`。
- **x64 系统调用约定**: `rax = 59 (execve)`, `rdi = "/bin/sh"`, `rsi = 0`, `rdx = 0`，然后触发 `syscall`。
- **x86 系统调用约定**: `eax = 11 (execve)`, `ebx = "/bin/sh"`, `ecx = 0`, `edx = 0`，然后触发 `int 0x80`。
- **优势**: 不需要 libc、不需要可执行栈、不需要后门函数，属于通用利用方法。
- **难点**: 需要找到足够的 gadget（`pop rax; ret`、`pop rdi; ret`、`syscall; ret` 等）。

### 4. Ret2libc (Return to libc)
- **原理**: 将返回地址覆盖为 libc 中的函数地址（如 `system`），并精心构造函数参数，实现 `system("/bin/sh")` 调用。
- **步骤**:
  1. 泄露 libc 中某函数的 GOT 地址（通过 puts/write 输出 GOT 条目）。
  2. 根据泄露值计算 libc 基址。
  3. 从 libc 中获取 `system` 地址和 `"/bin/sh"` 字符串地址。
  4. 构造 ROP 链: `pop rdi; ret` + `"/bin/sh"` + `system`。
- **变种**: Ret2libc 也可以调用 libc 中的 `execve`、`one_gadget` 等。
- **防御**: ASLR 下需要先泄露地址；Full RELRO 下 GOT 只读。

### 5. Ret2csu (Return to CSU - __libc_csu_init)
- **原理**: 利用 glibc ELF 文件 `__libc_csu_init` 函数中存在的通用 gadget（称为 csu gadget）来设置 rbx/rbp/r12/r13/r14/r15 寄存器，然后通过 `call [r12+rbx*8]` 间接调用函数。
- **经典 csu gadget**:
  - `pop rbx; pop rbp; pop r12; pop r13; pop r14; pop r15; ret` (控制各寄存器)
  - `mov rdx, r14; mov rsi, r13; mov edi, r12d; call [r15+rbx*8]` (设置调用参数并调用)
- **用途**: 当程序 gadget 稀少（如静态编译、仅 PLT 可用）时，csu gadget 提供了构造完整函数调用的可能性。
- **限制**: r15 + rbx\*8 指向的内存必须是可读的，且其中保存着可调用的函数地址。

### 6. Ret2VDSO (Return to VDSO)
- **原理**: VDSO (Virtual Dynamic Shared Object) 是内核映射到每个用户态进程地址空间中的一个小型共享库，用于加速某些系统调用（如 `clock_gettime`、`gettimeofday`）。Ret2VDSO 利用 VDSO 中的代码片段来实现某些功能。
- **场景**: 在 libc 不可用或需要绕过某些检测机制时使用。
- **局限性**: VDSO 中可用的 gadget 非常有限，且地址随机化强度较高，实用性有限。

### 7. SROP (Sigreturn-Oriented Programming)
- **原理**: 利用信号机制中的 `sigreturn` 系统调用，将伪造的 `sigframe` 从栈上恢复到寄存器中，一次性设置所有寄存器的值，然后继续执行。
- **步骤**:
  1. 在栈上构造伪造的 `sigframe`（包含 rax/rdi/rsi/rdx/rip/cs/eflags 等寄存器值）。
  2. 将返回地址设置为 `syscall; ret` gadget 的地址，此时 rax 需要设置为 15 (SYS_rt_sigreturn)。
  3. 执行 sigreturn 后，所有寄存器的值从伪造的 sigframe 中恢复。
  4. 设置 rip 为 `execve` 系统调用的入口，rax 为 59，其他参数为 `/bin/sh` 相关值。
- **优势**: 一次设置所有寄存器，无需复杂的多步 ROP 链构造；可绕过某些 gadget 不足的限制。
- **工具**: pwntools 提供了 `SigreturnFrame()` 类方便构造 sigframe。

### 8. dl_runtime_resolve 利用
- **原理**: 利用动态链接器的延迟绑定（Lazy Binding）机制，伪造 `_dl_runtime_resolve` 的参数，使其解析攻击者指定的函数名，并将其 GOT 条目指向攻击者指定的地址。
- **步骤**:
  1. 在可写区域（如 .bss 段）伪造一个 `Elf64_Rela` 条目，其中包含目标函数名称字符串的偏移。
  2. 伪造函数名字符串（如 "system"）。
  3. 构造调用链: 调用 PLT [0]（PLT 跳转表入口）+ 伪造的 reloc_offset。
  4. 动态链接器会解析出 `system` 的实际地址并调用之。
- **优势**: 在 libc 版本未知或无法泄露 libc 地址时依然可以使用；完全不需要知道 libc 版本。
- **限制**: 需要 .bss 段有足够的可写空间；Partial RELRO 下才能工作（Full RELRO 下 GOT 只读，延迟绑定已禁用）。

### 9. Stack Pivoting (栈迁移)
- **原理**: 当栈空间不足（如只能覆盖到返回地址但无法构造完整的 ROP 链）或栈地址不便利用时，通过修改 RSP/ESP 寄存器将栈转移到攻击者控制的区域（如堆、全局变量区），在新栈上继续执行 ROP 链。
- **常用 gadget**: `leave; ret`（相当于 `mov rsp, rbp; pop rbp; ret`）。
- **步骤**:
  1. 在堆或其他可写区域精心构造 ROP 链。
  2. 将 RBP 设置为该区域的地址。
  3. 通过 `leave; ret` 将 RSP 指向 RBP，从而将栈切换到攻击者控制的区域。
  4. RSP 指向新栈上的 ROP 链，继续执行。
- **场景**: 栈溢出空间有限（仅覆盖 EBP+返回地址）；第二次栈溢出用于构造更大的链。

### 10. Canary 绕过 (Stack Canary Bypass)
- **原理**: Stack Canary（也称 Stack Guard）是在函数序言中设置的栈保护值，在函数返回前检查其是否被篡改。若被篡改则调用 `__stack_chk_fail` 终止程序。
- **绕过方法**:
  1. **泄露 Canary**: 利用格式化字符串、越界读、未初始化内存泄露等方式获取 Canary 值，然后在覆盖时保持原值。
  2. **爆破 Canary**: 在多线程/多进程场景中（fork 保持 Canary 不变），逐字节爆破 Canary。每个字节 256 种可能，最多需要 256\*8 = 2048 次尝试。
  3. **覆盖 TLS 中的 Canary**: Canary 值同时存储在 TLS 段中，若存在任意地址写能力，可直接覆盖 TLS 中的 Canary。
  4. **不触发检查**: 通过覆写函数指针、修改 `__stack_chk_fail` 的 GOT 条目、或利用 longjmp 绕过正常的 epilogue 检查流程。
  5. **SSP (Stack Smashing Protection) 绕过**: 利用 `__stack_chk_fail` 中的 `__fortify_fail` 会输出 argv[0] 的特性，将 `argv[0]` 覆盖为目标内存地址，可以实现有限的信息泄露（Stack Smashing 技巧）。

## 防御/对抗建议

- **Stack Canary**: 编译时启用 `-fstack-protector`（GCC/Clang），对所有包含局部数组的函数启用 Canary 保护。
- **ASLR**: 对所有内存区域实施随机化，提高地址泄露的难度。
- **NX**: 确保栈不可执行，防止 Ret2shellcode。
- **PIE**: 开启位置无关可执行文件，使得代码段地址随机化。
- **RELRO**: 开启 Full RELRO 禁用延迟绑定，防御 `dl_runtime_resolve` 攻击。
- **FORTIFY_SOURCE**: 使用 `-D_FORTIFY_SOURCE=2` 启用编译时的缓冲区溢出检测。

## 示例/思路

### 基础 Ret2libc 利用链
```
# Stage 1: 泄露 libc 地址
overflow padding + pop_rdi_ret + puts_got + puts_plt + vuln_addr

# Stage 2: 计算基址 + 执行 system("/bin/sh")
overflow padding + pop_rdi_ret + bin_sh_addr + system_addr
```

### Canary 泄露 + 绕过
```
# 假设存在格式化字符串漏洞
# 偏移量 X 处可以泄露出 Canary 值
payload = b"%X$p"  # 泄露 Canary
leak = int(recv(), 16)
payload = b"A"*offset + p64(leak) + p64(0) + p64(win_addr)
```
