# 代码注入 (Code Injection)

## 概述

代码注入（Code Injection）是一种在目标进程中执行任意代码的技术，广泛应用于软件安全研究、恶意软件对抗、游戏外挂开发以及逆向工程中的动态分析场景。通过代码注入，攻击者可以在目标进程的地址空间中执行代码，访问其内存、修改其数据、Hook 其函数。

在 CTF 逆向中，代码注入技术有助于理解恶意软件行为、分析被保护程序的运行时逻辑、以及开发动态分析辅助工具。同时，代码注入本身也是逆向工程分析的常见对象（当被分析程序使用了注入技术时）。

---

## 常见注入手法

### 1. 远程线程注入 (Remote Thread Injection)
- **原理**: 使用 `CreateRemoteThread` 函数在目标进程中创建一个新线程，线程起始地址设为 `LoadLibrary`（DLL 注入）或 Shellcode 地址。
- **步骤**:
  1. 打开目标进程（`OpenProcess`）。
  2. 在目标进程中分配内存（`VirtualAllocEx`）。
  3. 将 DLL 路径或 Shellcode 写入分配的内存（`WriteProcessMemory`）。
  4. 调用 `CreateRemoteThread`，线程函数地址为 `LoadLibraryA/W` 或 Shellcode 入口。
- **检测**: 通过监控 `CreateRemoteThread` + `LoadLibrary` 调用对；监控跨进程的 `VirtualAllocEx` + `WriteProcessMemory`。
- **绕过**: 使用 `NtCreateThreadEx` 替代 `CreateRemoteThread`；使用 SetWindowsHookEx 的替代方法。

### 2. DLL 注入 (DLL Injection)
- **原理**: 强制目标进程加载指定的 DLL，DLL 的 `DllMain` 在目标进程中执行。
- **常见方法**:
  - **`CreateRemoteThread` + `LoadLibrary`**: 经典方法。
  - **`SetWindowsHookEx`**: 设置全局钩子，钩子 DLL 会被注入到所有满足钩子条件的进程中。
  - **AppInit_DLLs (注册表)**: 设置 `HKLM\Software\Microsoft\Windows NT\CurrentVersion\Windows\AppInit_DLLs` 注册表值，所有加载 `user32.dll` 的进程都会加载指定的 DLL。
  - **Image File Execution Options (IFEO)**: 设置特定进程的 `Debugger` 或 `GlobalFlag` + `Loader` 注入。
  - **COM 劫持**: 让目标进程实例化特定的 COM 组件，触发恶意 DLL 加载。
- **检测**: 监控进程加载的所有 DLL 模块；检测 DLL 的加载时间与正常加载时序不符。
- **绕过**: 使用反射式 DLL 注入（不通过 `LoadLibrary`，手动解析和加载 DLL）。

### 3. IAT Hook (Import Address Table Hooking)
- **原理**: 修改 PE 文件导入表中函数地址，将对原始函数的调用重定向到攻击者的函数。
- **步骤**:
  1. 定位目标进程的 IAT（导入地址表）。
  2. 将目标函数的 IAT 条目修改为 Hook 函数的地址。
  3. 当程序调用该导入函数时，实际执行的是 Hook 函数。
- **用途**: 监控 API 调用、修改函数行为、绕过安全检查。
- **限制**: 只能 Hook 导入表中存在的函数；延迟加载（Delay-Load）的导入可能尚未解析。
- **检测**: 比较 IAT 中的函数地址与其真实地址是否一致。

### 4. Inline Hook (内联钩子)
- **原理**: 在目标函数的机器码开头写入跳转指令（JMP/CALL），使其跳转到攻击者的 Hook 函数。
- **步骤**:
  1. 保存目标函数开头的 N 字节（通常为 5-14 字节，取决于跳转指令长度）。
  2. 在目标函数开头写入 `JMP HookFunc` 指令。
  3. 在 Hook 函数中处理调用逻辑后，执行原始保存的指令并跳转回原函数 +N 位置。
  5. 可选: 制作"Trampoline"用于保留调用原始函数的通道。
- **x86 典型**: `JMP rel32`（5 字节）或 `PUSH addr; RET`（6 字节）。
- **x64 难点**: 需要 64 位绝对跳转（如 `MOV RAX, addr; JMP RAX`，12 字节）。
- **检测**: 检查代码段的可执行区域是否有非预期的跳转指令；比较函数入口的机器码与原始代码。
- **绕过**: 使用 `hot patch`（利用函数开头的 2 字节 NOP 预留空间）；只 Hook 函数的特定调用路径。

### 5. Process Hollowing (进程镂空)
- **原理**: 创建一个合法进程（如 `svchost.exe`），在其未开始执行前，将其主模块的内存内容替换为恶意代码，然后恢复进程执行。
- **步骤**:
  1. 创建挂起的合法进程（`CreateProcess(CREATE_SUSPENDED)`）。
  2. 获取进程主模块信息（NtQueryInformationProcess）。
  3. 卸载原始主模块（`NtUnmapViewOfSection` 或 `ZwUnmapViewOfSection`）。
  4. 分配新内存（`VirtualAllocEx`），写入恶意 PE 的内容。
  5. 重写进程的入口点（`SetThreadContext` 修改 EAX/RIP 为恶意 PE 入口点）。
  6. 恢复线程继续执行（`ResumeThread`）。
- **用途**: 以合法进程的名义执行恶意代码，绕过基于进程名的检测/白名单。
- **检测**: 监控进程创建后主模块内存内容的异常替换；检查进程实际入口点与文件入口点是否一致。
- **变种**: AtomBombing、Asynchronous Procedure Call (APC) + Process Hollowing 组合。

### 6. Message Hook (消息钩子)
- **原理**: 通过 `SetWindowsHookEx` 设置 Windows 消息钩子，将恶意 DLL 注入到处理特定消息的所有进程中。
- **钩子类型**:
  - `WH_KEYBOARD` / `WH_KEYBOARD_LL`: 键盘钩子（按键记录/注入）。
  - `WH_MOUSE` / `WH_MOUSE_LL`: 鼠标钩子。
  - `WH_GETMESSAGE`: 消息循环钩子。
  - `WH_CALLWNDPROC`: 窗口过程钩子。
- **注意**: 全局钩子（`dwThreadId = 0`）要求钩子 DLL 必须导出全局内存中的数据段。
- **检测**: 系统中的进程加载了不应加载的 DLL。

### 7. APC 注入 (Asynchronous Procedure Call Injection)
- **原理**: 将恶意代码以 APC（异步过程调用）的形式排队到目标线程的 APC 队列中，当线程进入可警告等待状态时执行该代码。
- **步骤**:
  1. 打开目标线程（`OpenThread`）。
  2. 在目标进程中分配内存并写入 Shellcode/DLL 路径。
  3. 使用 `QueueUserAPC` 将 APC 函数排入线程队列。
  4. 目标线程进入可警告等待状态（`WaitForSingleObjectEx`/`SleepEx`/`MsgWaitForMultipleObjectsEx` 等）时触发 APC 执行。
- **高级变种**: **Full APC Injection** - 将所有线程排队 APC，即使当前不在等待状态，后续也会在 I/O 操作时触发。
- **检测**: 监控可疑的 `QueueUserAPC` 调用和跨进程内存分配。

### 8. DLL 反射加载 (Reflective DLL Injection)
- **原理**: DLL 自身实现了从内存中加载自身（无需通过 Windows 的 `LoadLibrary` API），避免了标准 DLL 加载路径的监控。
- **DLL 内部必须实现**:
  1. 解析自身 PE 结构。
  2. 在调用进程的地址空间中分配内存。
  3. 解析导入表和进行重定位。
  4. 调用 `DllMain` 初始化。
- **优势**:
  - 不调用 `LoadLibrary`，绕过基于该 API 的检测。
  - 无需将 DLL 写入磁盘（纯内存加载）。
  - 不易被用户态 API 监控系统捕获。
- **检测**: 监控内存分配（`VirtualAlloc`）+ 大量 PE 解析操作；检测代码段中的 PE 结构特征。

### 9. SSDT Hook (System Service Descriptor Table Hook)
- **原理**: 修改内核的 SSDT（系统服务调度表），将对内核系统调用的处理重定向到恶意代码。
- **用途**:
  - 隐藏进程/文件/注册表（Rootkit 常用）。
  - 监控和过滤敏感系统调用。
  - 修改系统调用的返回结果。
- **步骤**:
  1. 获取 SSDT 基址（通过 `KeServiceDescriptorTable`）。
  2. 禁用写保护（修改 CR0 寄存器的 WP 位）。
  3. 替换指定系统服务号的函数指针。
  4. 恢复写保护。
- **检测**: 比较 SSDT 中的函数地址与内核模块中该函数的实际地址（`MmGetSystemRoutineAddress`）。
- **绕过**: 使用内核回调机制（`CmRegisterCallback`、`PsSetCreateProcessNotifyRoutine`）替代 SSDT Hook。

### 10. 其他代码注入技术
- **AtomBombing**: 利用 GlobalAddAtom/GlobalGetAtomName 的原子表机制传递 Shellcode，结合 APC 注入执行。
- **Thread Execution Hijacking (线程劫持)**: 挂起目标线程，修改其上下文（Context）中的指令指针指向 Shellcode，然后恢复线程。
- **Extra Window Memory (EWM)**: 在 Windows 窗口的额外内存中存储 Shellcode，利用 `SetWindowLong`/`CallWindowProc` 执行。
- **PROPagate**: 利用 Windows 的 Property 系统（`SetProp`/`EnumProps`）实现注入。
- **COM 劫持**: 修改 COM 组件的 CLSID 注册，使应用程序加载恶意 COM 对象。

## 防御/对抗建议

- **DLL 加载监控**: 监控非标准的 DLL 加载行为（无对应磁盘文件、加载时机异常）。
- **API 调用监控**: 监控 `CreateRemoteThread`、`VirtualAllocEx`、`WriteProcessMemory`、`SetWindowsHookEx` 等敏感 API。
- **进程完整性检查**: 检查进程入口点是否与文件入口点一致；定期校验代码段的哈希。
- **启用缓解技术 (Mitigation)**: 
  - **ACG (Arbitrary Code Guard)**: 阻止分配新的可执行内存。
  - **CIG (Code Integrity Guard)**: 只允许签名的 DLL 加载。
  - **Block Non-Microsoft DLL**: 阻止第三方 DLL 注入到系统进程中。
- **内核态防护**: 检测 SSDT 篡改；使用 PatchGuard (KPP) 保护内核代码完整性。
- **用户态 Hook 检测**: 扫描 IAT 和 Inline Hook；比较函数地址的真实性。
