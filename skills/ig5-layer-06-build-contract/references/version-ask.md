# 版本号串：先问用户（提问模板与三档默认）

> 本文件是**强制条款**的落地模板。任何「定/改版本号串与产物命名」的动作都要先走这里。
> 来源：用户自有项目的历史构建笔记（已洗掉项目标识）。核心教训是「AI 别自己上版本号规则」。

## 为什么必须先问

版本号串与产物命名是**用户工作流的一部分**（下载器排序、群里对版本、CI 缓存键、发布页对照）。
AI 自选一套「更规范」的格式，会打断用户已有的肌肉记忆；而这类改动一旦发出，回滚成本高（用户已经按旧格式发过版本）。

## 提问模板（照抄，按用户语言）

```
版本号与产物命名我按你现有习惯来，先确认三件事（一句话回复即可，或直接说「你定」）：
1) 工程版本号格式：纯 semver（1.2.3）／ semver + 构建时间戳（1.2.3-20260930-2226）／ 其他（写出来）
2) 产物文件名：是否要带 时间戳 / 7 位哈希 / 构建类型后缀（-debug / -beta）；release 要不要后缀
3) 发布一致性：tag、发布页、产物名是否必须同源（由构建阶段算一次、发布阶段直接用 output）
```

## 三档默认（只在用户说「你定」时用）

| 档 | 工程版本 | 产物名 | 适用 |
|---|---|---|---|
| A 最小 | `1.2.3` 手维护 + 整数 `versionCode` | `<名>-<工程版本>[-debug].apk` | 个人项目、只自己装 |
| B 可追溯（默认推荐） | `1.2.3` | `<名>-<工程版本>-<yyyyMMdd-HHmm>-<7位哈希>[-buildType].apk` | 会分发、要能回指某次构建 |
| C 极简 | 只递增整数 | `<名>-<整数>.apk` | 内部工具、不对外 |

选 B 时固定时区（写进脚本，别依赖本机），并从构建阶段注入、发布阶段复用，避免「三处三个版本」。

## 反面清单（做之前先看一眼）

- ❌ 没问就改**已有**格式（哪怕只是把 `1.2.3` 换成 `v1.2.3`）。
- ❌ 把语义化版本当默认正确 —— 它只是一种约定。
- ❌ 产物名里悄悄加/去时间戳、哈希、分支名。
- ❌ 让 `git rev-parse` 在配置阶段跑（配置缓存会挂）—— 版本参数应由脚本注入环境变量。
- ❌ 发布阶段**重算**版本号 —— 必须复用构建阶段的 output，否则 tag / 产物 / 发布页会各说一套。
