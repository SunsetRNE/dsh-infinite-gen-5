## 三、红队段：inline hook / 热补丁的检出（架构 · 步骤 · 代码 · 验证）

### 3.1 架构

对照的是两份「同一地址的字节」：一份来自**磁盘镜像**，一份来自**目标进程内存**。磁盘镜像的导出地址由导出表自己给出（`AddressOfFunctions[i]` + `AddressOfNames` 反查），内存地址由 `模块基址 + RVA` 得到，两者不需要调试符号，也不依赖 PG/驱动。

```
磁盘: IMAGE → 导出表 → RVA → rvaToOffset → 文件偏移处的前 N 字节 ─┐
                                                                ├─ 逐字节 diff → 分类 → 报告
内存: 进程 → 模块枚举 → modBaseAddr + RVA → ReadProcessMemory ──┘
```

### 3.2 步骤

1. 枚举目标进程已加载模块，取 `modBaseAddr`（`CreateToolhelp32Snapshot` + `Module32FirstW/NextW`）。
2. 用磁盘镜像解析导出表，得到 `(name, ordinal, rva)` 三元组。
3. 对每个导出取磁盘前 `SCAN_BYTES` 字节作为基线，再 `ReadProcessMemory` 同地址同长度。
4. 逐字节 diff；不等即分类（见下表），打印 `[HOOK] module= export= addr= disk= mem=`。
5. 对命中模块补扫：解析 `.text` 段，按 16 字节步进整段哈希，找同一文件其他被改点。
6. 交叉确认：对可疑地址读回原字节做反汇编（`dumpbin /disasm` 或 `ndisasm`），确认补丁长度与跳转目标。

### 3.3 补丁手法与判别信号（示例字节均为常量/magic，非本机观测值）

| 补丁手法 | 示例字节（常量/magic） | 判别信号 | 检出命令 |
| --- | --- | --- | --- |
| jmp rel32 热补丁 | 示例：首字节常量 `0xE9`（JMP_REL32），后跟 4 字节 rel32 | 首字节不在磁盘基线中 | `pecheck --pid TARGET_PID` |
| jmp [rip+disp] | 示例：常量 `0xFF 0x25` + disp32 | 6 字节长度、无 rel32 | 同上 |
| mov rax,imm64 + jmp rax | 示例：常量 `0x48 0xB8` … `0xFF 0xE0` | 10 字节长度 | 同上 |
| int3 断点 | 示例：常量 `0xCC`（INT3） | 单字节替换，易被 EDR 回填 | 同上 + 整段哈希 |
| 跳板式（detour 落在外部分配页） | 示例：`0xE9` 指向非模块区间 | 跳转目标不在任何已加载模块范围内 | `pecheck --pid TARGET_PID` + 模块区间比对 |

### 3.4 验证方法

- **阳性对照**：`hookself.exe` 对自身导出 `pev_alpha` 写入 `JMP_REL32` 补丁并停住，`pecheck.exe --pid <它打印的 PID> --module hookself.exe` 必须报出该导出 → rc=1。
- **阴性对照**：直接对未做任何改动的 `testdll.dll` 宿主进程跑同一命令 → 无 `[HOOK]` 行、rc=0；若阴性也报，先怀疑基线长度与节对齐，不要先怀疑「检测到了新手法」。
- **解析器侧对照**：`peverify` 的四类退出码（0/1/5/6）已在本机实测，保证「磁盘基线」这一段本身是对的。

### 3.5 扩大

- 对每个导出扫完再扫整段 `.text`（256 字节块 SHA-256），能捞到**未通过导出调用的**被改函数。
- 同进程读两份映射：`ReadProcessMemory` 与 `NtReadVirtualMemory` 比对，识别只在某一 API 路径上被回填的实现（DBI/沙箱常见）。
- 交叉验证可从 `\KnownDlls`、`SEC_IMAGE` 节对象重映射一份干净映像再比对，绕开被改写的进程内映像。
